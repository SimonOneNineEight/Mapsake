Canonical memory + audit trail for this PRD run. Every decision, change, and override lands here as the conversation unfolds.

## 2026-07-02 — Pre-PRD decisions (made with Simon in conversation, before workspace bind)

- **v2 form:** native iOS app, Swift/SwiftUI (stack lean to be RATIFIED in architecture phase; Simon explicitly chose Swift over React Native/Expo after a tradeoff review — key reasons: UI/UX uplift is a core v2 goal (SwiftUI's native feel), iOS-first with Android unscheduled, the UI is being redesigned anyway so React component carryover is moot, widget potential).
- **Scope posture:** v1 feature parity + native push notifications (APNs) + a deliberate UI/UX uplift. (Simon initially picked "rethink the product," then revised: the rethink he wanted was specifically the UI/UX redesign, not product discovery.) Deferred v1 backlog (GeoNames search, en locale, 2-8 merge, offline) stays post-v2 unless discovery says otherwise.
- **v1 web app:** stays running against the same backend; native app is the retention surface, web remains the instant-access front door. Backend (Supabase, eligibility engine, cron sender, auth) carries over unchanged — new backend changes must stay compatible with both clients.
- **Distribution:** iOS first via the App Store; Android deferred (with Swift chosen, Android later = a second build — accepted with eyes open).
- **Candidate native-only feature:** an "on this day" home-screen widget (flagged as the best product-fit native capability; in-scope question for this PRD).
- **Design workflow (refined 2026-07-02 after researching Claude Design):** UX phase follows this PRD. Mockups live in a "Mapsake v2" **Claude Design** project (claude.ai/design — Anthropic's design studio, verified accessible via DesignSync from this session): the design system (palette/type/components) is pushed as iPhone-viewport preview cards; Simon reviews AND edits directly (WYSIWYG canvas + inline comments + chat), Claude folds changes back into code. Export-to-Figma exists if Simon ever wants Figma ownership. A served tap-through HTML prototype on Simon's iPhone complements the canvas for flow-feel. Converged screens become the SwiftUI implementation reference. Caveats noted: beta (comments occasionally flaky), no iPhone viewport presets (we set ~390pt cards ourselves).
- **v1 learnings carried in:** anonymous-first worked on web (open question: first-run on iOS where an App Store install already signals intent); the re-live push loop is the product's soul (verified end-to-end in prod 2026-07-02); iOS web push was the weak link motivating v2.

## 2026-07-02 — Journey-derived decisions (coaching path)

- **UJ-1 capture model:** post-trip logging ritual (not in-the-moment capture). Search-first placement (v1's deferred 3-2 search PROMOTED to v2 core), visit date, date-suggested photo picking (never forced), per-place loop with a session-end recap. Save-success animation at the capture-confirm moment.
- **Multi-visit pins:** one place → many visits (each with date + photos). Woven through all journeys; research confirms no comparable models this cleanly (differentiator). Backend/data-model change on the SHARED backend — web compatibility is a v2 architecture concern.
- **UJ-2 re-live:** photo-rich APNs notification ("N 年前的今天" + that day's photo as the image); tap lands on THAT DATE's visit; calm ending, no streaks/feed.
- **UJ-3 browse:** map-first + search; browse-all surface becomes first-class navigation (not hidden); geographic hierarchy (continent→country→region→place) replaces the messy alphabetical list. No trip entity — geography is the organizing spine.
- **UJ-4 first-run:** warm intro (2-3 screens) → **signed-in-first (one-tap Apple/Google; NO anonymous mode on iOS — Simon confirmed)** → guided first memory (a real memory with note+photos REPLACES v1's region-tap backfill as the onboarding payoff) → recap + contextual notification permission ask (the one clean OS prompt, primed by visible value). Sign in with Apple is REQUIRED alongside Google (App Store rule for apps with third-party login).
- **Form factor:** iPhone-targeted for v2 launch; SwiftUI written adaptively (size-class-aware) so real iPad support is an incremental v2.x layout pass. Web app remains the anonymous try-first front door; the two clients deliberately play different roles.

## 2026-07-02 — Read-only map (Simon's proposal, during PRD review)

- **The map is read-only on iOS; memories are the only write path.** Region marking as a user action is REMOVED. Visited fill = derived from memories ∪ legacy web region-marks (iOS reads marks, never writes them). Backfill = batch name-only ("empty") memories via the capture loop run light. Sole map write gesture = **long-press → add a memory here** (option (a), confirmed).
- Why: kills the tap-semantics phase-blocker outright (tap always reads → no accidental marks while panning, Simon's real v1 pain); halves the write model (one write type instead of marks+pins with roll-up interplay); philosophically right for 時光膠囊 (map = display case, memories = contents).
- Costs accepted with fixes: web compat via read-only derivation of legacy marks; two new open questions replace the blocker (empty-memory placement granularity; re-live down-weighting of contentless memories so batch backfill can't flood the capsule).
- **Post-v2 intent (Simon):** if the v2 model proves out, rewrite the v1 web app to align with it. Not a v2 deliverable; noted in PRD §1.
